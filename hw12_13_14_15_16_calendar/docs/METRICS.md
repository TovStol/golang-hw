# Мониторинг Календаря - Документация по метрикам

## Обзор

Сервис календаря инструментирован с использованием Prometheus для сбора метрик. Все метрики доступны через эндпоинт `/metrics` в формате Prometheus.

## HTTP Метрики

### `calendar_http_requests_total`

**Тип:** Counter  
**Лейблы:** method, path, status  
**Описание:** Общее количество HTTP запросов к API.

**Зачем важно:** Позволяет отслеживать нагрузку на сервис, выявлять аномалии в трафике, определять популярность эндпоинтов и мониторить количество ошибок по статус-кодам.

**Использование для анализа:**
- Мониторинг общего объема запросов
- Выявление всплесков трафика
- Анализ распределения запросов по методам и путям
- Отслеживание процентного соотношения ошибок (4xx, 5xx)

### `calendar_http_request_duration_seconds`

**Тип:** Histogram  
**Лейблы:** method, path  
**Описание:** Время обработки HTTP запросов в секундах.

**Зачем важно:** Позволяет анализировать производительность API, выявлять медленные эндпоинты и отслеживать изменения во времени отклика.

**Использование для анализа:**
- Определение медленных эндпоинтов (p95, p99)
- Выявление деградации производительности
- Оптимизация самых нагруженных путей
- SLA мониторинг (например, 95% запросов должны обрабатываться за < 100ms)

## Бизнес-метрики событий

### `calendar_events_created_total`

**Тип:** Counter  
**Описание:** Общее количество созданных событий.

**Зачем важно:** Отражает активность пользователей в создании событий, помогает понять популярность сервиса.

### `calendar_events_updated_total`

**Тип:** Counter  
**Описание:** Общее количество обновленных событий.

**Зачем важно:** Показывает частоту изменений в существующих событиях.

### `calendar_events_deleted_total`

**Тип:** Counter  
**Описание:** Общее количество удаленных событий.

**Зачем важно:** Помогает понять паттерны использования и частоту очистки календаря.

## Метрики Scheduler (фоновые задачи)

### `calendar_scheduler_runs_total`

**Тип:** Counter  
**Описание:** Общее количество запусков планировщика.

**Зачем важно:** Показывает, как часто планировщик сканирует события для отправки уведомлений. Всплески или отсутствие запусков могут указывать на проблемы.

### `calendar_scheduler_notifications_sent_total`

**Тип:** Counter  
**Описание:** Общее количество уведомлений, отправленных планировщиком в Kafka.

**Зачем важно:** Отражает успешную работу по отправке уведомлений. Отсутствие роста может указывать на проблемы с Kafka или отсутствие событий для уведомления.

### `calendar_scheduler_events_processed_total`

**Тип:** Counter  
**Описание:** Общее количество событий, обработанных планировщиком.

**Зачем важно:** Показывает объем работы планировщика. Сравнение с `notifications_sent_total` помогает выявить проблемы при отправке.

### `calendar_scheduler_errors_total`

**Тип:** Counter  
**Описание:** Общее количество ошибок планировщика.

**Зачем важно:** Критическая метрика для мониторинга здоровья фоновых задач. Рост этой метрики требует немедленного внимания.

## Метрики Storer (consumer)

### `calendar_storer_notifications_received_total`

**Тип:** Counter  
**Описание:** Общее количество уведомлений, полученных из Kafka.

**Зачем важно:** Показывает, что storer успешно читает из Kafka. Отсутствие роста может указывать на проблемы с consumer group или Kafka.

### `calendar_storer_notifications_stored_total`

**Тип:** Counter  
**Описание:** Общее количество уведомлений, сохраненных в базу данных.

**Зачем важно:** Отражает успешное сохранение уведомлений. Разница с `notifications_received_total` показывает процент потерь при сохранении.

### `calendar_storer_errors_total`

**Тип:** Counter  
**Описание:** Общее количество ошибок storer.

**Зачем важно:** Критическая метрика для мониторинга здоровья consumer. Рост требует проверки подключения к БД или проблем с Kafka.

## Визуализация

Для визуализации метрик используется Prometheus, который автоматически собирает метрики с эндпоинта `/metrics` каждые 15 секунд.

**Запуск Prometheus:**
```bash
cd deployments
docker compose up prometheus
```

**Доступ к веб-интерфейсу Prometheus:**
```
http://localhost:9090
```

## Примеры запросов для анализа

### Среднее время ответа API
```
rate(calendar_http_request_duration_seconds_sum[5m]) / rate(calendar_http_request_duration_seconds_count[5m])
```

### Процент ошибок (5xx)
```
sum(rate(calendar_http_requests_total{status=~"5.."}[5m])) / sum(rate(calendar_http_requests_total[5m])) * 100
```

### Количество созданных событий в минуту
```
rate(calendar_events_created_total[1m])
```

### Эффективность отправки уведомлений
```
calendar_scheduler_notifications_sent_total / calendar_scheduler_events_processed_total
```

## Рекомендации по мониторингу

1. **Настройте алерты:**
   - Высокий процент ошибок 5xx (> 5%)
   - Отсутствие запусков scheduler (> 5 минут)
   - Рост storer_errors_total
   - Превышение p95 latency (> 1s)

2. **Регулярно анализируйте:**
   - Тренды использования (создание/обновление/удаление событий)
   - Производительность эндпоинтов
   - Эффективность pipeline уведомлений

3. **Используйте дашборды:**
   - Обзор системы (requests, errors, latency)
   - Бизнес-метрики (создание событий)
   - Pipeline уведомлений (scheduler → Kafka → storer)
